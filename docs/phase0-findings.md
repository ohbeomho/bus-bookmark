- [확인] **존재하지 않는 정류장, 미지원 도시, 잘못된 도시코드, 운행 노선 없음이 전부 똑같이 "0건"으로 온다.** 응답만으로는 "도착 정보가 없음"과 "정류장/도시가 잘못됨"을 구분할 수 없다.
- [확인] 기본 `numOfRows`는 100 (body에 echo됨). 한 정류장 노선이 100개를 넘는 경우는 보지 못했다 (최대 10건).

### 정규화 코드 영향

`items` 가 문자열("")일 때 `items.item` 접근은 `undefined` 이므로 아래 순서가 안전하다.

1. `resultCode !== "00"` 이면 오류.
2. `const it = body.items?.item;`
3. `it == null` 이면 `[]`, `Array.isArray(it)` 이면 그대로, 아니면 `[it]`.

## 6. PRD 가정과 다른 점, 위험

1. **서울(11) 미지원**: PRD 가정(12장 위험)대로 확인됨. 서울/미목록 지역 사용자는 도착정보를 못 받는다. 이 경우 API는 오류가 아닌 0건을 주므로 **지원 여부는 `cities.json`(도시코드 목록)으로 앱이 직접 판단**해야 한다 (PRD 3장 ③의 빌드 시 1회 조회 방침이 필수가 됨).
2. **0건이 오류와 구분되지 않음**: 잘못된 nodeId와 심야 무운행이 같은 응답이다. UI 문구는 "도착 정보가 없어요" 정도로 하고, 정류장 존재 여부는 타일 데이터 기준으로 판단한다.
3. **item이 1건이면 객체, 0건이면 빈 문자열**: CLAUDE.md의 정규화 규칙이 실제로 필요함이 확인됨.
4. **`routeno` 가 숫자 타입**: PRD/문서에서 문자열로 가정했다면 수정 필요. 항상 `String()` 변환.
5. **응답이 arrtime 순이 아님**: 정렬 로직 필요.
6. **HTTP 522 일시 오류**: Worker의 502 외에 Cloudflare 에지 오류가 평문으로 올 수 있어 재시도(1회)는 유효하다. 본문이 JSON이 아니어도 앱이 깨지지 않게 파싱 예외를 처리해야 한다.
7. **API 키 활용신청 범위**: 정류소정보 등 다른 서비스는 별도 활용 신청 필요. 현재 앱 설계(CSV + 도착정보)에는 불필요하나, CSV를 못 쓰게 될 경우의 대안이 막혀 있다.
8. Worker 응답에 캐시 헤더는 확인하지 못했다 (`Cache-Control` 미관측). [추측] 필요하면 Worker 쪽에서 짧은 캐시를 붙여 호출 한도를 아낄 수 있다 (코드 수정은 이번 범위 아님).
9. `.gitignore` 에는 `scripts/raw/` 만 있고 PRD/지시의 `data/raw/` 는 없다. CSV를 `data/raw/` 에 둘 거라면 `data/raw/` 도 추가해야 한다 (전국 CSV는 수십 MB 규모로 예상되나 [추측], 배포 대상이 아니고 연 1회 갱신되는 원본이라 커밋하지 않는 쪽을 권장).

## A. CSV 구조 [확인]

- 좌표: 위도 33.208~38.304, 경도 125.984~130.916. 0 또는 결측 0건, 한국 범위 밖 0건. 이상값 없음.

결론: **CSV의 `정류장번호`와 `도시코드`를 그대로 nodeId/cityCode로 넣으면 대전과 제주 모두 도착정보가 온다. CSV의 정류장명과 응답 `nodenm`은 5개 정류장에서 모두 일치했다.**

제주 응답에서 새로 확인된 점 (대전과 다른 점):

- `arrtime`이 **전부 60의 배수**(분 단위로 반올림된 값)다 (60, 120, 180, 240, 300 ...). 대전은 12초, 93초 같은 초 단위 값이었다. 초 단위 카운트다운 UI는 제주에서 "정확한 초"처럼 보이면 안 된다 (분 단위 표시 권장).
- **같은 `routeno`가 한 정류장 응답에 여러 번** 나온다 (제주 341 x2, 181 x2, 202 x3, 501 x2, 212 x2). 이들은 `routeid`가 서로 다르다 (예: 202 → JEB405320217 / ...219 / ...237). `routeid` 중복은 없었다. **노선을 `routeno`로 식별하면 안 된다**는 CLAUDE.md 규칙이 실제로 필요함이 확인됐고, 즐겨찾기 키와 화면 목록 key는 `routeId`여야 한다. 같은 번호 노선은 화면에서 구분이 필요할 수 있다 (방면 정보는 응답에 없음).
- `routeid` 형식: 제주 `JEB405130002` (접두사 JEB + 9자리).
- `routetp`: 간선버스, 급행버스, 지선버스. `vehicletp`: 일반차량, 저상버스. `routeno`는 제주에서도 숫자(Int)였다.
- 응답 건수는 제주 시내 중심 정류장에서 18~19건으로 대전(최대 11건)보다 많다. `numOfRows` 100 기본값 안이다.
- 522가 대전 첫 호출에서 다시 발생했다 (한동안 호출이 없다가 첫 호출). 두 번 모두 재시도에서 성공하므로 [추측] 콜드스타트성 일시 오류다. 재시도 1회는 필수로 보인다.

## E. Phase 1 타일 전처리에 미치는 영향

- 입력은 **EUC-KR 디코딩 필수**, 따옴표 인식 CSV 파서 필요, CRLF 처리.
- 0.05° 격자 기준 전국 **3,822개 타일** (비어 있지 않은 칸). 타일당 정류장 수 중앙값 32, 최대 1,002 (서울·부산 중심부). 최대 타일은 행당 약 60바이트 가정 시 60KB 안팎 [추측, 크기는 미측정]이므로 큰 도시 중심부는 타일 분할(격자 0.025° 등)이나 gzip 전제가 필요할 수 있다. 전체 22.3MB 원본 대비 타일 JSON 합계는 ARS·이름 포함 시 약 15~20MB로 추정 [추측].
- **ARS 결측이 많다** (전체 10.8%, 제주는 100%). 타일 배열의 ARS 칸은 빈 문자열 또는 null을 허용하고, "0"도 결측으로 취급해야 한다. 검색·표시 로직에서 ARS를 필수로 가정하지 말 것.
- 정류장번호는 전국 유일하고 문자열(접두사 포함)이다. 숫자로 변환하지 말 것.
- `정류장명`은 같은 이름이 방면별로 여러 개다 (대전역 x2, 제주시청 x2 등). 지도에서 근접 정류장을 구분하려면 방면 정보가 이름 괄호에 있을 때만 의존할 수 있다.
- 좌표 이상값이 없으므로 이상값 필터는 불필요하나, 방어적으로 한국 범위 검사를 넣어도 비용이 적다.
- `index.json`의 수집일은 CSV의 `정보수집일`(2026-11-09)을 쓸 수 있다.
- 도시코드 필터: 위 D항의 23개 코드를 포함할지 정책이 필요하다 (서울은 17,082행으로 전체의 7.5%).

## F. 갱신된 결론

- Phase 0 완료 기준 ③~⑤: 대전과 제주에서 CSV→Worker→도착정보 연결이 **확인됐다.** 다른 도시(부산, 대구 등)는 호출하지 않았으므로 미확인이다.
